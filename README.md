# DocIntel — RAG Document Intelligence System

A real, functional Retrieval-Augmented Generation (RAG) application. Users register/login,
upload PDFs, and ask natural-language questions that are answered using only the content
of their own uploaded documents, with accurate page-level source citations.

Nothing here is mocked: text extraction runs on real PDFs (PyMuPDF), embeddings are
generated by a real Sentence Transformers model, similarity search runs on a real FAISS
index, and answers come from a real LLM call grounded in retrieved chunks.

## Features

- Email/password registration and login (bcrypt-hashed passwords, JWT auth)
- Drag-and-drop PDF upload with background processing and live status polling
- Page-aware text extraction, cleaning, and sentence-aware chunking
- Batched embedding generation (Sentence Transformers, model loaded once and reused)
- FAISS `IndexFlatIP` similarity search over normalized (cosine) embeddings, persisted to disk
- MongoDB Atlas as the system of record for users, documents, chunks, conversations, messages
- Strict per-user data isolation on every read/write path
- Chat interface with conversation history, per-query document filtering, and expandable
  source cards showing document name, page number, similarity score, and text preview
- Grounded answers only — if nothing relevant is retrieved, the app says so instead of
  guessing

## Architecture

```
React (Vite) UI  --REST-->  FastAPI backend
                                 |
                +----------------+----------------+
                |                |                 |
          Authentication   Document Pipeline   RAG Pipeline
                |                |                 |
           MongoDB Atlas     PyMuPDF          Query Embedding
                              |                    |
                          Cleaning            FAISS Search
                              |                    |
                          Chunking            Top-K Chunks
                              |                    |
                          Embeddings          Context Build
                              |                    |
                            FAISS                 LLM
                                                    |
                                          Answer + Sources
```

FAISS stores only vectors + a local id-mapping/tombstone file. MongoDB Atlas is the
source of truth for every piece of metadata (who owns what, which page a chunk came
from, etc.). The link between the two is the integer `faiss_index` stored on each
`chunks` document.

## RAG pipeline (upload → answer)

1. Upload PDF → validate type/size → save to disk → create `documents` record (`uploaded`)
2. Background task: extract text per-page (PyMuPDF), preserving page numbers
3. Clean text (whitespace, broken line wraps, page-number noise)
4. Chunk text (configurable size/overlap, sentence-boundary aware)
5. Generate embeddings in batches (Sentence Transformers, normalized for cosine similarity)
6. Add vectors to the FAISS index, persist index to disk
7. Insert chunk metadata (with `faiss_index`) into MongoDB, mark document `processed`
8. On question: embed the query → FAISS search → filter results by user/document + score
   threshold in MongoDB → build LLM context → call LLM with a strict grounded-QA system
   prompt → return answer + real sources → persist both to `messages`

## Tech stack

**Frontend:** React, Vite, Tailwind CSS, React Router, Axios, Lucide React
**Backend:** FastAPI, Uvicorn, Pydantic, PyMongo/Motor, PyMuPDF, Sentence Transformers,
FAISS, python-jose (JWT), passlib/bcrypt
**Database:** MongoDB Atlas (no SQLite, no SQLAlchemy)
**Vector search:** FAISS (`IndexFlatIP`), persisted to disk

## MongoDB Atlas setup

1. Create a free/shared cluster at https://www.mongodb.com/cloud/atlas
2. Create a database user (username/password)
3. Under **Network Access**, allow your current IP (or `0.0.0.0/0` for local dev only)
4. Copy the connection string ("Drivers" → Python) — this is your `MONGODB_URI`
5. Pick a database name (e.g. `rag_document_intelligence`) — this is `MONGODB_DATABASE`

Collections (`users`, `documents`, `chunks`, `conversations`, `messages`) and all
indexes are created automatically on backend startup (see `app/database/mongodb.py`).

## FAISS setup

No external service required. On first run, `app/services/vector_store.py` creates a
new `IndexFlatIP` sized to the embedding model's dimension and persists it to
`backend/storage/vector_indexes/global.index`, alongside `metadata.json` (tombstoned
vector positions used for document deletion). Both are recreated automatically if
missing, and reloaded automatically on the next startup.

## Backend setup

```bash
cd backend
python3 -m venv .venv
source python3 -m venv .venv     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # then edit .env with real values
```

The first request that needs embeddings will download the Sentence Transformers
model (`all-MiniLM-L6-v2` by default, ~80MB) — this happens once and is cached locally.

## Running locally (full stack)

1. Start MongoDB Atlas (cloud, always on) — just make sure your IP is allowed
2. `uvicorn app.main:app --reload --port 8000` (backend)
3. `npm run dev` (frontend)
4. Register an account, upload a PDF, wait for status to become `processed`, then ask
   questions in the Chat page

## Database structure

See `backend/app/models/*.py` for the exact document shapes stored in MongoDB
(`users`, `documents`, `chunks`, `conversations`, `messages`), matching the spec:

```
User → Document → Page → Chunk → FAISS Vector
```

`chunks.faiss_index` is the integer position of that chunk's vector inside the FAISS
index — the single source of truth for the FAISS↔MongoDB mapping.

## Vector search explanation

Embeddings are L2-normalized before being added to a FAISS `IndexFlatIP` (inner-product)
index, which makes inner product mathematically equivalent to cosine similarity. A
query is embedded and normalized the same way, then searched against the index. Results
are filtered in MongoDB to the requesting user's own documents (and optionally a
specific document subset) and to a configurable similarity threshold before being sent
to the LLM.

## Authentication architecture

```
React → FastAPI → JWT verification → MongoDB Atlas
```

- Passwords are hashed with bcrypt (`passlib`) — never stored or logged in plain text
- `POST /api/auth/login` and `/register` issue a JWT containing only the user's id (`sub`)
- Every protected route depends on `get_current_user`, which decodes and verifies the
  JWT and loads the user from MongoDB — **the authenticated user id always comes from
  the token, never from a request body or query parameter**
- The frontend stores the token in `localStorage` and attaches it as a `Bearer` header
  via an Axios interceptor; a 401 response clears the token and redirects to `/login`

## Deployment

**Backend (Render or similar):**
- Build command: `pip install -r backend/requirements.txt`
- Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT` (run from `backend/`)
- Set all `backend/.env.example` variables as environment variables in the dashboard
- Attach a persistent disk mounted at `backend/storage` if you want uploads/FAISS index
  to survive restarts/redeploys (otherwise re-upload documents after each redeploy)

**Frontend (Vercel or similar):**
- Root directory: `frontend`
- Build command: `npm run build`, output directory: `dist`
- Set `VITE_API_BASE_URL` to your deployed backend URL

**MongoDB Atlas:**
- Under Network Access, allow your deployment platform's IP range (or `0.0.0.0/0` if
  your plan requires it, understanding the security tradeoff)

**CORS:** set `CORS_ORIGINS` on the backend to your deployed frontend's exact origin
(e.g. `https://your-app.vercel.app`) so the browser is allowed to call the API.

## Troubleshooting

- **"No extractable text was found in this PDF"** — the PDF is scanned/image-only;
  OCR isn't implemented in this version (see Future improvements)
- **Login works but every other request 401s** — check `VITE_API_BASE_URL` matches the
  backend, and that the JWT hasn't expired (`JWT_EXPIRE_MINUTES`)
- **`LLM_API_KEY is not configured`** — set it in `backend/.env` and restart the backend
- **Mongo connection fails on startup** — check `MONGODB_URI`, the Atlas Network Access
  allow-list, and that your database user's password doesn't contain unescaped special
  characters
- **First query is slow** — the embedding model loads lazily on first use; subsequent
  requests reuse the cached in-memory model
